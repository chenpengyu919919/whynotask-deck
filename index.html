02 / 为什么难

难的不是识别，是判断

三个矛盾，任何一个走极端，demo 立刻变玩具。
点开看我们的回答。

矛盾一：主动与打扰。没有价格机制，就只能二选一——要么不开口，要么变成骚扰。我们的答案是给每次开口算分。

我们的三条回答

01 / 给每次开口定价Δ 打分 + 频率预算 + 拒绝抑制。说不出理由的那句话，就不说；每次“该说没说”都留一条决策记录。
02 / 理解归模型，动作过闸门模型只能产出结构化理解，执行器只接受带 ALLOW 判决的请求。中间那层是规则，不是提示词。
03 / 把代价写在明面上6 秒延迟、DMS 没有真机曲线、长跑只到 8 分钟——这些写在验收文档“未完成”一节里，而不是藏起来。

三条都不是靠调参解决的，
是靠结构。

主动、安全、离线三项能力互相拉扯：任何一项单独拿满分，另两项就会崩。

03 / 两张手稿

一张纸定“怎么答”，一张纸定“该不该说”

左：V2.0 的用户主动交互。
右：V3.0 的主动服务与 Δ 打分。

V2.0用户主动交互语音 → ASR → embedding → LLM → 安全层 → TTS
  • 纸上有：ASR → 语义 → 匹配功能 → 安全层通过/拒绝 → 库存够播切片、不够现合成
  • 后来补：先判“谁在对谁说”；embedding 只召回 top-3 功能名；判决四档；通过后还要执行与回读
V3.0主动服务与 Δ麦克风 / 摄像头 / 车况 → Δ 打分 → 静默或开口

04 / 系统结构

三条链路，一个执行入口

点一列，看它真正做的关键动作。
三条链最后都汇到同一道闸门。

共同点 / 三条链共用同一个执行入口（safety/gate.py → execution/executor.py）。这是“任意模型输出都不能绕过安全约束”的结构保证，而不是一句承诺。

状态模型（世界模型）/ 把观测收成“带来源与时效的情境状态”：三场景派生 + 冲突标记 + 质量分级，同一份状态同时喂给 Δ 打分与九步闸门。新增一路观测（例如贴耳通话 dms.phone_call）只是多一个事实——不多一分权限。

两条判断都不能省：打分回答“值不值得”，闸门回答“能不能”。

05 / 判断原理

先决定值不值得，再决定能不能做

悬停、聚焦或点击流程节点。
公式项与右侧决策状态同步变化。

Δ =S_e·A_f·V_f+T_w+B_c−C_i·L
S_e证据强度：说了什么、谁在说
A_f · V_f适用性与价值：此时此地值多少
T_w时机：驻车、充电窗口为正
B_c预算：间隔、冷却、每小时上限
C_i打扰成本：车态、模式、是否通话
L打断乘数：我们刚播报过 ×4
四重限流最小间隔同类冷却每小时上限拒绝冷却
DECISION / 决策状态
当前场景：行车　·　节点：判断

10 / 运行期事故

跑起来才现形的三个错

不是代码评审挑出来的，是跑久了、跑真了才现形。
点一条看日志证据。

三条都是“跑久了才现形”的事故，证据是日志条数、面板对比与 TTS 时长；另有 18 条开发期踩坑，写在同一份清单里。

时间戳回绕：视觉看护静默停摆

现象机器连续开机约 28 小时后，DMS 不再产出任何结果；面板没有报错、也没有 unavailable 事件，看起来“一切正常”。
根因时间戳写成 int((monotonic() % 100000) * 1000)，在 uptime ≈ 100 000 秒处回绕；MediaPipe 发现时间戳非单调后拒绝继续，日志里留下 263 条每 5 秒一次的报错。
改成什么换成进程相对时间基准，并对同一 landmarker 强制递增；重建失败后显式降级为“不可用”，health() 只在确有新帧时才报 ok。
谁抓到的运行日志连续错误计数 + 看门狗告警
三条都留下了可复查的痕迹：日志条数、面板对比、TTS 时长——不是“感觉修好了”。

11 / 硬件边界

被硬件卡住的地方

真车、真摄像头、真麦克风——三样都不在手上。
这些不是没做，是缺条件。

01没有上真车：只有软件执行器改的是内存里的设备状态，没有 CAN / 串口 / 固件，回执一律标“软件演示”。需要一台可接管的车与台架，并在台架上重跑 18 条时间线。
02DMS 没有真机人脸曲线EAR / PERCLOS 的基线与阈值来自工程经验与合成陆标；摄像头不对准驾驶员时只会显示“不可用”。需要固定机位 + 真实疲劳实验曲线。
03手持通话的贴耳阈值没标定ear_radius 默认 1.05，是“手到耳距离 ÷ 双耳像素间距”的经验值；真车机位下没量过，挠头、托腮可能误报。需要真车 + phone_probe.py 现场取距离。
04单麦克风判不了说话人speaker 只能是 unknown_speaker，旁座说话靠“交流对象判断”兜，不是声源定位。需要麦克风阵列 / 波束成形。

硬件不到位时，该说的是“这条还没验”，而不是“应该没问题”。

硬件到位后先做三件事

① 台架复跑 18 条时间线 + 74 项测试，抓“只在真车上才现形”的分支。

② 用真实疲劳曲线重标 EAR / PERCLOS 的基线与阈值，把误报率写进验收。

③ 用真车摄像头标 ear_radius，再决定贴耳判定要不要更细的姿态过滤。

不靠硬件的欠账在别处

端到端 6 秒（第 9 页）、检索补位没单独评测（第 8 页）、holdout 只覆盖文本层、面板不是产品级前端——这些是软件与评测的活。

真车 / 真机 / 真麦克风三件事都没到位；凡是能靠写代码解决的，都已经写在验收文档里并有测试盯着。
